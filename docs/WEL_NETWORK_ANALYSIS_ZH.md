# WEL / WRH 对战平台网络链路完整分析与开发基准

> 文档版本：2026-08-13  
> 适用仓库：`welopenvpn-clean` 与配套 `platform` API  
> 当前生产方案：`WE8 Socket Hook + TAP-Windows + n2n edge/supernode`  
> 后续候选方案：`WE8 全双工 Socket Hook + 用户态房间传输`，不安装虚拟网卡

## 1. 文档目的

本文档是 WEL / WRH 对战平台网络部分的长期开发基准，回答以下问题：

1. 玩家进入房间后，虚拟 IP、TAP、n2n、路由和防火墙分别负责什么。
2. WE8 建主、客机搜索、主机回复、客机加入和正式联机时，数据包从哪里产生、经过哪里、最终交给谁。
3. 当前 `welhook.dll` 实际 Hook 了什么，没有 Hook 什么。
4. 当前已经配置了哪些 Windows 防火墙规则，Windows 7 与 Windows 10/11 有什么差异。
5. 如何用成功抓包作为基准，定位“搜不到、只能直连、Ping 不通、能搜到但连不上”等问题。
6. 将来去掉 TAP/n2n 虚拟网卡时，Hook 版本必须实现哪些网络语义，才能继续让游戏认为玩家处于同一局域网。

本文档严格区分：

- **已由抓包证实**：主客机成功样本中确实出现的行为。
- **当前代码已实现**：仓库当前版本已经具备的逻辑。
- **设计要求或待验证项**：未来方案或尚未通过失败样本确认的内容。

## 2. 最小必读结论

### 2.1 WE8 的主客机协议轮廓

本次成功抓包确认 WE8 使用 IPv4 UDP，主机固定监听 `5739`，客机使用随机源端口。

搜索主机：

```text
客机虚拟IP:随机端口  ->  房间定向广播IP:5739    UDP 24 字节
主机虚拟IP:5739      ->  客机虚拟IP:原随机端口  UDP 136 字节
```

加入和正式联机：

```text
客机虚拟IP:另一个随机端口  <->  主机虚拟IP:5739
```

关键事实：

- **主机不会周期性广播自己存在。**
- **客机先发搜索广播，主机收到后再单播回复。**
- 搜索阶段和加入阶段可以使用不同的客机随机端口。
- 不能只转发 `5739 -> 5739`。
- 必须允许并保留“随机端口 -> `5739`”和“`5739` -> 原随机端口”。
- 搜索广播成功不代表正式联机成功，后续还有持续双向 UDP。

### 2.2 当前方案的职责边界

```text
平台 API
  分配房间、community、唯一虚拟 IP
        |
        v
n2n edge + TAP-Windows
  建立房间二层虚拟局域网，搬运以太网帧
        |
        v
welgame.exe + welhook.dll
  让 WE8 的 UDP Socket 绑定 TAP IP
  把 255.255.255.255:5739 改为房间定向广播地址
        |
        v
Windows 防火墙和路由
  允许房间 UDP/ICMP，确保 10.222.x.0/24 指向 TAP
```

### 2.3 当前方案已经证明能工作的部分

成功样本中已经完成：

- 后端唯一虚拟 IP 分配。
- TAP 网卡启用和静态 IP 配置。
- 两端 ARP 学习。
- WE8 Hook 注入并加载。
- 客机搜索广播进入 TAP。
- n2n 把广播交给主机 TAP。
- 主机 WE8 从 `5739` 回复客机随机端口。
- 客机加入主机并持续双向交换 UDP。
- n2n 从 supernode 协调切换为两端物理地址直接 P2P。
- Windows 防火墙开启、默认阻止入站时，WEL 规则允许该样本正常工作。

### 2.4 成功样本不能证明的部分

这两台电脑处于同一个真实局域网 `192.168.3.0/24`。因此该样本不能单独证明：

- 异地双 NAT、运营商 CGNAT、对称 NAT 下的 P2P 成功率。
- supernode 中继在所有失败网络中的可用性。
- 第三方虚拟网卡抢路由时一定不会冲突。
- 杀毒软件、企业组策略或第三方防火墙不会拦截 Hook、TAP、edge。
- Windows 7 上所有本地安全策略都能接受规则写入。

出现真实失败时，必须让失败双方同时抓包，再与本文成功链路逐层比较。

## 3. 抓包样本与测试环境

### 3.1 样本文件

客机：

```text
WEL网络诊断-Client-B-20260813-192825.welcap.zip
抓包时间：2026-08-13 19:28:27 至 19:32:53
```

主机：

```text
WEL网络诊断-Host-A-20260813-192924.welcap.zip
抓包时间：2026-08-13 19:29:28 至 19:33:20
```

两个时间区间有约 3 分钟重叠，覆盖了启动游戏、主机建房、客机搜索、加入和持续联机。

### 3.2 地址与接口

| 项目 | 客机 Client-B | 主机 Host-A |
|---|---:|---:|
| TAP IPv4 | `10.222.1.10/24` | `10.222.1.11/24` |
| TAP MAC | `00-FF-35-92-90-9B` | `00-FF-A0-0B-81-8E` |
| TAP ifIndex | `3` | `12` |
| TAP MTU | `1290` | `1290` |
| 物理 WLAN IPv4 | `192.168.3.89` | `192.168.3.124` |
| n2n 物理 UDP 端口 | `58987` | `49263` |
| WE8 角色 | 搜索、加入方 | 建主、监听方 |
| WE8 PID | `18964` | `1980` |

主机抓包开始时 TAP 尚未连接、没有虚拟 IP，随后进入房间后变为 `10.222.1.11/24`。这说明抓包覆盖到了 TAP 拉起过程。

### 3.3 路由状态

两端最终都有以下房间路由：

```text
10.222.1.0/24      -> 本机 TAP
本机 TAP IP/32     -> 本机 TAP
10.222.1.255/32    -> 本机 TAP
255.255.255.255/32 -> 本机 TAP
```

默认路由仍然是：

```text
0.0.0.0/0 -> 192.168.3.1 -> WLAN
```

因此当前设计不会把网页、直播和普通互联网流量整体送入 TAP。只有房间网段及被 WE8 Hook 绑定到 TAP 的游戏流量走虚拟局域网。

### 3.4 防火墙状态

两端 Windows 防火墙均处于启用状态，三个配置文件的默认策略为：

```text
BlockInbound, AllowOutbound
```

本次成功不是依赖关闭防火墙，而是在防火墙开启状态下由 WEL 放行规则完成。

### 3.5 PktMon 数据解释注意事项

- PktMon 会在 Windows 网络栈多个组件重复记录同一个包，不能把文本行数当成真实网络包数。
- ETL 停止日志显示“无事件丢失”，但客机捕获统计中还出现了捕获层丢包计数；严格做时序或丢包率分析时应优先使用主机完整样本，并减少无关流量。
- 客机日志中出现本机广播副本相关的 `transport endpoint was not found`、`Port unreachable`、`ICMP: invalid source`。
- 这些提示不等于隧道失败，因为同一个搜索广播已经离开客机 TAP、到达主机，主机也完成了有效回复。
- 判断成败必须追踪同一五元组在两端是否出现，不能只看到一条 PktMon DropReason 就下结论。

## 4. 当前系统完整架构

### 4.1 控制面

控制面由平台 API 和数据库负责：

1. 用户进入房间时，API 在事务中锁定房间和用户会话。
2. 每个房间使用独立 `/24`：
   - 房间 1：`10.222.1.0/24`
   - 房间 2：`10.222.2.0/24`
   - 依此类推，当前共 6 个房间。
3. 可分配范围为每房间 `.10` 至 `.109`。
4. `room_ip_leases` 对 `(room_id, virtual_ip)` 设置唯一约束，避免同房间 IP 冲突。
5. API 使用可串行化事务和 `nextFreeIP` 选择未占用地址。
6. 租约包含 `room_id`、`virtual_ip`、`subnet_cidr`、`community`、用户标识和有效期。
7. 房间租约默认有效期为 30 分钟，客户端心跳续期。
8. n2n community 默认按房间隔离，形式为 `wel-room-<roomID>`，API 也可以下发显式 community。

控制面只分配逻辑身份和地址，不承载游戏实时数据。

### 4.2 数据面

当前数据面分为两层：

#### 内层：游戏虚拟局域网

```text
以太网帧
  源/目标 TAP MAC
IPv4
  10.222.<房间>.<玩家>
UDP
  主机 5739，客机随机端口
WE8 原始载荷
```

#### 外层：n2n 传输

```text
n2n 封装后的 UDP
  物理网卡 IPv4:随机端口
      <-> supernode:22222
  或  <-> 对端物理/公网地址:随机端口
```

游戏只看到内层 `10.222.x.x` 网络，不知道外层是局域网直连、互联网 P2P 还是经过 supernode 协调。

### 4.3 服务端职责

n2n supernode 当前地址：

```text
8.155.145.132:22222/UDP
```

其职责是节点注册、发现和 NAT 穿透协调。抓包显示本次两端随后建立了直接传输：

```text
192.168.3.89:58987 <-> 192.168.3.124:49263/UDP
```

这说明本次游戏帧不需要持续绕行中心服务器。实际异地网络能否直连取决于双方 NAT；不能把本次同局域网直连结果外推到所有玩家。

## 5. 进入房间的当前实现

### 5.1 TAP 检测与复用

客户端按以下顺序检测现有 TAP：

1. 使用 `tapctl list` 枚举 TAP 设备。
2. 枚举失败时读取网络适配器注册表。
3. 注册表受限时使用 WMI 查询。
4. 使用 TAP 设备 GUID 作为权威标识，网卡显示名称只作为辅助信息。
5. 记住安装器创建的 GUID 和上次成功使用的 GUID。
6. 已存在 TAP 时启用并复用，不应因为名称本地化或绿色版换目录而重复创建。
7. 只有确实没有可用 TAP 时才调用内置安装程序。

n2n 3.0 在 Windows 上打开 TAP 时依赖设备 GUID；GUID 大小写也被当前代码保留，避免传给 n2n 后匹配失败。

### 5.2 n2n edge 启动参数

当前客户端构造的核心参数为：

```text
edge.exe
  -d <TAP设备GUID>
  -E
  -x 1
  -c <房间community>
  -l <supernode主机>:22222
  -a <平台分配虚拟IP>/<前缀>
  -t 5645
  [-p <物理出口IP> -e <物理出口IP>]
  [-k <传输密钥>]
  -I <用户/设备标识>
```

其中：

- `-d` 指定 WEL 选中的 TAP 设备，而不是依赖任意网卡名称。
- `-a` 把 API 分配的静态虚拟 IP 配置到 TAP。
- `-c` 隔离不同房间。
- `-l` 指向统一的 n2n supernode。
- `-E` 允许虚拟网络需要的组播 MAC 行为。
- `-x 1` 设置 n2n/TAP 相关 metric 参数。
- `-p/-e` 使用到 supernode 的最佳物理出口 IPv4，约束 n2n 外层 UDP 的物理出口。

这里必须区分两个“绑定”：

- **n2n 外层绑定物理网卡**：让发往 supernode/对端的封装 UDP 走正常 WLAN/以太网。
- **WE8 内层绑定 TAP 网卡**：让游戏的 `10.222.x.x` UDP 进入虚拟局域网。

绝不能把 n2n 外层 Socket 绑定到 TAP。否则 n2n 为了运送 TAP 帧又把自身传输送回 TAP，会造成递归或完全无法出网。

### 5.3 连接成功判定

客户端最多尝试 4 次，每次最长约 45 秒。只有同时满足以下条件才返回“已连接”：

1. `edge.exe` 仍在运行。
2. 系统出现属于当前房间 CIDR 的 IPv4。
3. 实际 TAP IP 与 API 分配的 `virtualIP` 一致。
4. 能通过 WMI/系统接口信息识别该地址的 ifIndex 和 MAC。

连接后保存当前网络信息，供启动 WE8 时传给 Hook。

### 5.4 房间路由修正

连接完成后执行等价于：

```text
route change <房间网络> mask <子网掩码> <本机TAP-IP> metric 1 if <TAP-ifIndex>
```

若路由不存在则执行 `route add`。

目的：

- 把 `10.222.<房间>.0/24` 显式钉到当前 WEL TAP。
- 避免 ZeroTier、Radmin VPN、其他 TAP、旧 OpenVPN 等第三方虚拟网卡抢占相同或更宽的路由。
- 不修改默认路由，不影响普通互联网流量。

路由修正当前属于尽力而为逻辑。修正失败不会中止已建立的 n2n 连接，因此遇到多网卡疑难问题时仍要检查最终路由表，而不能只看平台显示“已进入房间”。

## 6. 游戏启动与 Hook 注入

### 6.1 启动流程

当前平台不是直接执行 `WE8.exe`，而是调用 `welgame.exe`：

```text
welgame.exe
  --game <WE8.exe>
  --hook <welhook.dll>
  --tap-ip <本机虚拟IP>
  --broadcast-ip <房间定向广播IP>
  --interface-index <TAP ifIndex>
```

`welgame.exe` 的实际流程：

1. 校验游戏和 Hook DLL 路径。
2. 设置环境变量：
   - `WEL_TAP_IP`
   - `WEL_BROADCAST_IP`
   - `WEL_TAP_INTERFACE_INDEX`
   - `WEL_HOOK_READY_EVENT`
3. 以 `CREATE_SUSPENDED` 创建 WE8。
4. 在 WE8 进程中分配内存并写入 `welhook.dll` 路径。
5. 使用 `CreateRemoteThread + LoadLibraryW` 注入 DLL。
6. 等待 Hook 初始化完成事件，最长 5 秒。
7. Hook 未就绪则终止游戏，避免玩家在未绑定的状态下继续运行。
8. Hook 就绪后恢复 WE8 主线程。

成功抓包的进程模块时间线确认两边 `WE8.exe` 均加载了 `welhook.dll`。

### 6.2 Hook 的函数范围

当前 `welhook.dll` 通过 IAT 修补 Hook 以下 Winsock 函数：

```text
bind
connect
WSAConnect
send
WSASend
sendto
WSASendTo
```

初始化时修补 WE8 主模块，并每 250 毫秒枚举进程模块，对后加载模块继续修补。

当前没有 Hook：

```text
recvfrom
WSARecvFrom
recv / WSARecv
select / WSAEventSelect / WSAAsyncSelect
```

也没有解析、修改 WE8 游戏载荷。

### 6.3 UDP bind 强制绑定 TAP

对 WE8 内的 IPv4 UDP `bind()`：

- 回环地址 `127.0.0.1` 保持原样。
- 非 UDP Socket 保持原样。
- 其他 IPv4 UDP 绑定地址统一替换为 `WEL_TAP_IP`。
- 原端口保持不变，包括 `5739` 和由系统选择的随机端口。
- 同时通过 `IP_UNICAST_IF` 指定 TAP ifIndex。

示例：

```text
游戏请求 bind(0.0.0.0:5739)
Hook 实际执行 bind(10.222.1.11:5739)

游戏请求 bind(192.168.3.124:5739)
Hook 实际执行 bind(10.222.1.11:5739)
```

这解决多网卡环境下 WE8 绑定物理 WLAN、旧 VPN 或其他虚拟网卡的问题。

### 6.4 搜索广播重定向

WE8 原始搜索目标为：

```text
255.255.255.255:5739
```

Hook 仅在目标同时满足“IPv4、端口 `5739`、地址为全局广播”时改写为当前房间定向广播：

```text
10.222.<房间>.255:5739
```

改写前，Hook 检查该 UDP Socket 是否仍绑定 `0.0.0.0`。如果是，则保留原端口并将它绑定到 TAP IP，再设置 `IP_UNICAST_IF`。

所以成功抓包看到的是：

```text
10.222.1.10:52317 -> 10.222.1.255:5739
```

而不是物理 WLAN 上的：

```text
192.168.3.89:52317 -> 255.255.255.255:5739
```

### 6.5 房间单播绑定保护（v0.0.2）

`v0.0.2` 在不改变现有搜索广播路径的基础上，补齐 WE8 的房间单播 Socket 路径：

- `sendto/WSASendTo` 的目标位于当前房间子网时，发送前再次确认 Socket 已绑定 TAP。
- `connect/WSAConnect` 的 UDP 目标位于当前房间子网时，连接前绑定 TAP；这样也覆盖 connected UDP。
- `send/WSASend` 只在已连接 UDP 的对端位于当前房间子网时执行相同检查。
- 未绑定 Socket 即使 `getsockname()` 返回错误，也会以端口 `0` 绑定 TAP，由 Windows 分配随机端口。
- 非 UDP、IPv6、回环地址、物理局域网地址和互联网地址不进入这条新增逻辑。

房间范围由平台传入的 `WEL_TAP_IP + WEL_SUBNET_MASK` 判定。该限制用于避免把直播、浏览器或其他游戏外流量强制送进 TAP。

### 6.6 当前 Hook 的边界和风险

当前实现已保证：

- WE8 显式调用 `bind()` 的所有非回环 IPv4 UDP Socket 绑定 TAP。
- 搜索广播 Socket 即使原本依赖隐式绑定，也会在发送搜索包前强制绑定 TAP。
- 搜索目标从全局广播改为房间定向广播。
- 目标属于当前房间子网的普通单播和 connected UDP，在连接或发送前再次确认绑定 TAP。

当前实现没有单独保证：

- 接收路径能在没有 TAP 的情况下伪造来源 IP。
- 任意第三方模块通过动态 `GetProcAddress` 取得原始 Winsock 地址时一定经过 IAT Hook。
- 游戏网络如果实际由 WE8 之外的辅助进程持有，该进程一定会加载当前 Hook。

成功样本的加入 Socket 已实际使用 TAP 地址，说明 WE8 当前调用路径能被现有 Hook 覆盖。未来改 WE8 版本或替换网络组件时必须重新抓包验证，不能只凭旧版本结果推断。

## 7. Windows 防火墙规则

### 7.1 为什么不能只放行 UDP 5739

搜索请求的目标端口是 `5739`，但客机源端口是随机端口，主机回复目标也是该随机端口。正式联机继续使用：

```text
客机随机端口 <-> 主机 5739
```

同时 n2n 外层使用自己的随机 UDP 端口与 supernode/对端通信。因此只放行“本地端口 5739 入站”不足以覆盖整条链路。

当前策略是：

- 对房间虚拟网段放行全部 UDP 入站和出站。
- 对 `edge.exe` 放行入站。
- 对 WE8 精确程序路径放行入站。
- 对房间虚拟网段放行 ICMPv4，便于 Ping 与基础诊断。

### 7.2 Windows 7/10/11 统一规则（v0.0.4）

`v0.0.4` 不再使用 PowerShell COM 创建或验证防火墙规则。所有支持的 Windows 版本统一调用原生 `welfirewall.exe`，由它使用系统 `netsh advfirewall` 写入规则：

1. 辅助程序首次调用固定通过系统 `runas` 获取已提权令牌，避免 Win7 将“管理员组成员”误判成“当前进程已经提权”。
2. 平台已经提权时 Windows 直接复用权限；绿色环境权限不足时显示系统 UAC。
3. 不再依赖 `EncodedCommand`、PowerShell 模块初始化或 `HNetCfg.FwPolicy2`。
4. 因 PowerShell 被安全软件终止而产生的退出代码 `-1 (0xFFFFFFFF)` 不再阻塞进入房间。

进入房间时使用固定 `10.222.0.0/16` 创建以下规则；同一次平台运行只配置一次，切换房间不重复授权：

| 规则名 | 方向 | 协议 | 远端地址 | 端口 | 配置文件 |
|---|---|---|---|---|---|
| `WEL n2n edge inbound` | 入站 | 任意 | 任意 | 任意 | 全部 |
| `WEL room UDP inbound` | 入站 | UDP | `10.222.0.0/16` | 任意 | 全部 |
| `WEL room UDP outbound` | 出站 | UDP | `10.222.0.0/16` | 任意 | 全部 |
| `WEL room ICMPv4 inbound` | 入站 | ICMPv4 | `10.222.0.0/16` | 任意 | 全部 |
| `WEL room ICMPv4 outbound` | 出站 | ICMPv4 | `10.222.0.0/16` | 任意 | 全部 |

启动游戏时另外创建：

| 规则名 | 方向 | 协议 | 程序 | 地址/端口 | 配置文件 |
|---|---|---|---|---|---|
| `WEL WE8 inbound` | 入站 | 任意 | 当前选中的 `WE8.exe` 完整路径 | 任意 | 全部 |

`WEL WE8 inbound` 使用精确程序路径。玩家换了另一个 WE8 目录后，应以新路径重建规则。

### 7.3 WE8 显式 Block 冲突修复（v0.0.4）

Windows 防火墙中，同一程序同时存在 Allow 与 Block 时，显式 Block 优先。仅增加 `WEL WE8 inbound` 无法覆盖玩家以前在系统联网提示中选择“不允许访问”产生的规则。

因此每次通过平台启动游戏前，原生助手执行以下精确修复：

1. 只匹配当前选择的 `WE8.exe` 完整路径。
2. 只删除该路径的入站规则，不修改其出站规则。
3. 重新创建 `WEL WE8 inbound`：入站、任意协议、任意端口、Domain/Private/Public 全部允许。
4. 不删除其他 WE8 目录、其他游戏或其他程序的规则。

这覆盖“同一个 WE8 在其他平台可用，但 WEL 标准 TAP 到 Socket 路径被历史 Block 规则拦截”的情况。

### 7.4 规则设计的安全边界

这些规则不是全系统对互联网开放全部 UDP：

- 房间 UDP/ICMP 规则的远端地址限制在 WEL 分配的 `10.222.0.0/16`。
- `edge.exe` 入站规则只匹配打包的 edge 程序路径。
- WE8 入站规则只匹配玩家选择的游戏程序路径。
- 所有规则覆盖域、专用、公用配置文件，避免 TAP 被 Windows 识别为 Public 后失效。

### 7.5 验证要求

进入房间成功不能代替防火墙验证。故障诊断时必须确认：

1. 规则名称存在。
2. `Enabled = Yes`。
3. `Action = Allow`。
4. 配置文件包含 Public。
5. 远端地址覆盖当前 `10.222.x.0/24`。
6. `edge.exe` 和 `WE8.exe` 路径与当前实际路径一致。
7. 本地规则未被域 GPO 禁止。
8. 没有第三方安全软件在 Windows 防火墙之外继续拦截。

规则会在进入房间或启动游戏时重新写入，不依赖本地状态标记。若域 GPO 禁止本地规则或第三方安全软件独立拦截，`netsh` 规则成功仍不能覆盖该外部策略。

## 8. 成功联机逐包分析

### 8.1 阶段一：主机建主

主机 WE8 启动后：

```text
WE8.exe PID 1980
welhook.dll 已加载
UDP 监听：10.222.1.11:5739
```

这个 Socket 是主机发现和会话入口。主机此时不需要向房间周期广播自己的存在，只需能接收客机发来的搜索请求。

数据进入主机的接收路径：

```text
对端 n2n edge
  -> n2n 外层 UDP
  -> 主机 edge.exe 解封装
  -> 写入主机 TAP
  -> Windows IPv4/UDP
  -> 10.222.1.11:5739
  -> WE8.exe
```

### 8.2 阶段二：客机搜索

客机点击游戏搜索后生成：

```text
源 MAC：00-FF-35-92-90-9B
目标 MAC：FF-FF-FF-FF-FF-FF
源 IP/端口：10.222.1.10:52317
目标 IP/端口：10.222.1.255:5739
协议：UDP
载荷：24 字节
```

这里的 `52317` 是本次运行随机端口，不是固定协议端口。下一次运行会变化。

客机发送路径：

```text
WE8.exe 调用 sendto/WSASendTo(255.255.255.255:5739)
  -> welhook.dll 将目标改成 10.222.1.255:5739
  -> Hook 将 Socket/出口指定到 10.222.1.10 和 TAP ifIndex
  -> Windows 在 TAP 上生成广播以太网帧
  -> 客机 edge.exe 从 TAP 读取帧
  -> n2n 向同 community 的节点转发
  -> 主机 edge.exe 写入主机 TAP
  -> 主机 WE8 的 10.222.1.11:5739 收到 24 字节请求
```

### 8.3 阶段三：ARP 学习

主机收到搜索请求并准备回复 `10.222.1.10` 时，需要知道该虚拟 IP 对应的二层 MAC：

```text
主机：Who has 10.222.1.10?
客机：10.222.1.10 is at 00-FF-35-92-90-9B
```

ARP 也由 TAP 和 n2n 透明搬运。若搜索广播能到主机，但主机持续 ARP 无回复，则问题不在 WE8 载荷，而在二层回程、community、对端 edge/TAP 或广播/ARP 转发。

### 8.4 阶段四：主机回复搜索

主机从固定监听端口回复客机原随机端口：

```text
源 MAC：00-FF-A0-0B-81-8E
目标 MAC：00-FF-35-92-90-9B
源 IP/端口：10.222.1.11:5739
目标 IP/端口：10.222.1.10:52317
协议：UDP
载荷：136 字节
```

客机只有收到这类回复，游戏列表才会显示主机。

因此“客机发出了广播”只证明搜索请求出口正常，不证明能搜到。还必须继续确认：

1. 主机 TAP 收到广播。
2. 主机 WE8 的 `5739` Socket 收到广播。
3. 主机发出了 `5739 -> 客机随机端口` 回复。
4. 客机 TAP 收到回复。
5. 客机 WE8 Socket 收到回复。

### 8.5 阶段五：客机尝试加入

客机随后使用另一个随机端口：

```text
10.222.1.10:58880 -> 10.222.1.11:5739
```

主机回复：

```text
10.222.1.11:5739 -> 10.222.1.10:58880
```

加入阶段已经从广播发现切换为虚拟 IP 单播。此时“输入 IP 直连”与“从搜索列表连接”最终都会依赖这类单播会话。

### 8.6 阶段六：正式联机

抓包中 `58880 <-> 5739` 持续双向交换 UDP。载荷长度包括或接近：

```text
16, 22, 24, 28, 56, 60, 64, 68, 96, 100,
104, 120, 136, 280, 349, 351, 356, 560-600, 668 字节
```

这些长度可以用于判断链路是否进入持续会话，但本文不推断每种长度对应的游戏操作。平台不需要理解传球、比分、阵型或画面同步，只需透明、低延迟并保持 UDP 数据报边界地搬运载荷。

### 8.7 n2n 外层路径

本次 n2n 首先与以下 supernode 通信：

```text
8.155.145.132:22222/UDP
```

随后出现大量双向直接流量：

```text
客机 192.168.3.89:58987
    <->
主机 192.168.3.124:49263
```

外层 UDP 的包长与内层 WE8 数据不一一相等，因为还包括 n2n 头部、控制报文以及可能的帧封装。不要用“外层端口不是 5739”判断游戏端口错误。

## 9. 故障定位矩阵

### 9.1 基础分层

| 层级 | 正常证据 | 失败表现 | 优先检查 |
|---|---|---|---|
| API 租约 | 双方 IP 唯一且同 `/24` | IP 冲突、房间错误 | API 响应、数据库唯一约束、租约 |
| TAP | Up，地址正确 | NoTraffic、无地址、重复创建 | GUID、驱动、设备状态、edge 日志 |
| n2n 注册 | edge 存活，连接 supernode | 进房超时 | `edge.exe`、UDP 22222、安全组、物理出口 |
| n2n 二层 | 对端收到 ARP/广播 | Ping/搜索完全不通 | community、密钥、P2P/中继、防火墙 |
| Hook 注入 | WE8 模块有 `welhook.dll` | 广播仍走物理网卡 | 启动方式、DLL 架构、注入结果 |
| Socket 绑定 | WE8 监听 `10.222.x.x:5739` | 绑定 `0.0.0.0` 或物理 IP | Hook `bind`、ifIndex、TAP IP |
| 搜索请求 | 客机 TAP 发 `.255:5739` | 客机什么都不发 | 游戏操作、Hook sendto、Socket |
| 搜索回复 | 主机 `5739 -> 客机随机端口` | 广播到主机但无回复 | 主机 WE8、防火墙、ARP、主机状态 |
| 加入单播 | 双向 `随机端口 <-> 5739` | 能搜到但连接失败 | 单播路由、随机端口防火墙、回程 |
| 正式会话 | 持续双向不同长度 UDP | 进入后掉线/卡死 | 丢包、MTU、NAT、中继、性能 |

### 9.2 “Ping 不通，也搜不到，也不能直连”

这通常不是单纯搜索广播问题。优先检查：

1. 对方 TAP 是否 Up、IP 是否正确。
2. 双方是否同 community、同房间网段且 IP 不冲突。
3. 对方 Windows/第三方防火墙是否阻止整个 `10.222.x.0/24` 入站。
4. ARP 请求是否到达对方、ARP 回复是否回来。
5. n2n 是否只有单向数据。

### 9.3 “Ping 通，输入 IP 能连，但搜不到”

单播链路正常，问题集中在搜索广播：

1. 客机是否发 `TAP_IP:随机端口 -> 房间.255:5739`。
2. 是否仍发到物理网卡的 `255.255.255.255:5739`。
3. 主机是否收到广播。
4. 主机 WE8 是否监听 TAP 的 `5739`。
5. 主机是否回复客机原随机端口。

### 9.4 “能搜到，但连接失败”

广播和第一次回复已经正常，重点转到加入 Socket：

1. 客机是否产生新的随机端口到主机 `5739`。
2. 该 Socket 的源 IP 是否仍是 TAP IP。
3. 主机是否收到并回复该新随机端口。
4. 防火墙是否只放了搜索端口，没有放随机端口。
5. 第三方虚拟网卡是否抢走 `10.222.x.0/24` 单播路由。
6. MTU 或外层隧道是否只允许小包，较大正式会话包被丢弃。

### 9.5 “A 能搜到 B，B 搜不到 A”

这是典型单向问题，不能只检查两端 IP：

1. 分别确认两边当客机时的搜索广播出口。
2. 分别确认两边当主机时的 `5739` 监听地址。
3. 比较两边防火墙规则和网络配置文件分类。
4. 检查每个方向的 ARP 请求和回复。
5. 检查 n2n 外层是否双向。
6. 检查存在多个 TAP/ZeroTier/Radmin 时的路由和 ifIndex。

### 9.6 “关闭防火墙正常，开启后失败”

这已经足以把问题范围收敛到本机过滤层，不应继续修改游戏载荷或 n2n 协议。检查：

- WEL 规则是否真实存在并启用。
- 规则是否覆盖 Public。
- 房间远端网段是否正确。
- UDP 是否为任意本地/远端端口，而不是只放 `5739`。
- WE8 和 edge 程序路径是否变化。
- Windows 7 UAC 是否被取消。
- GPO 是否禁止本地防火墙规则。
- 第三方安全软件是否有独立网络过滤驱动。

## 10. 抓包工具的使用规范

### 10.1 标准测试步骤

1. 主机和客机都退出 WE8，保留平台可运行。
2. 两边分别启动 WEL 网络诊断工具。
3. 角色分别选择 `Host-A` 和 `Client-B`。
4. 两边点击开始抓包。
5. 两边从平台启动 WE8，确保走 `welgame.exe + welhook.dll`。
6. A 建主。
7. B 搜索，记录是否显示 A。
8. B 连接 A，A 接受。
9. 进入联机并维持至少 30 秒。
10. 两边点击停止并生成 `.welcap.zip`。
11. 同时记录防火墙开关、是否同真实局域网、运营商、路由器、其他虚拟网卡和实际故障现象。

### 10.2 分析优先级

每份包按以下顺序看：

1. `capture-info.txt`：时间和角色。
2. `start/end-ipconfig.txt`：TAP 是否拉起、IP 是否正确。
3. `start/end-interfaces.txt`：ifIndex、metric、MTU、状态。
4. `start/end-routes.txt`：房间路由和默认路由。
5. `start/end-firewall*.txt`：规则和配置文件。
6. `game-sockets-timeline.txt`：WE8/edge PID、模块和 Socket。
7. 最新 `wel-log-*.n2n.log`：edge 注册、TAP 和对端状态。
8. `packets.txt`：按虚拟 IP、`5739`、随机端口、外层 UDP 追踪。
9. 必要时用 Windows Wireshark 打开 PCAPNG，注意 PktMon 多组件重复记录。

### 10.3 一次失败样本必须回答的问题

```text
1. 客机搜索包有没有从 WE8 产生？
2. 客机 TAP 有没有发出？
3. 主机 TAP 有没有收到？
4. 主机 WE8 有没有收到？
5. 主机有没有从 5739 回复？
6. 客机 TAP 有没有收到回复？
7. 客机 WE8 有没有收到回复？
8. 加入阶段的新随机端口是什么？
9. 加入阶段两个方向分别断在哪一端？
10. n2n 外层是直连、经 supernode，还是根本没有对端数据？
```

只有回答完这些问题，才适合决定改 Hook、防火墙、路由、n2n 或服务端。

## 11. 未来无虚拟网卡 Hook 方案

### 11.1 可行性结论

根据成功抓包，平台不需要分析 WE8 的比赛操作和游戏状态。无 TAP 版本只需完整复现 Socket 层可见的局域网语义：

- 同房间每个玩家有唯一逻辑 IP。
- 客机广播搜索能扇出给房间内所有主机。
- 主机回复能回到发起搜索的准确客机 Socket。
- 后续单播数据报能持续双向转发。
- WE8 看到的来源地址仍是对端逻辑 IP 和原始端口。

因此方案可行，但它不是“只 Hook 广播 sendto”这么简单。

### 11.2 推荐架构

```text
WE8.exe
  |
  | Hook Winsock 发送、接收、等待事件
  v
welhook.dll
  |
  | 本机 IPC，共享内存/命名管道/本地 UDP
  v
WEL 用户态房间代理
  |
  | 加密 UDP/QUIC/WebRTC DataChannel 等传输
  v
房间中继或 P2P 对端代理
```

平台 API 继续负责房间成员、逻辑 IP 和授权。数据代理负责包转发，不理解 WE8 载荷。

### 11.3 出站 Hook 契约

至少覆盖：

```text
socket / WSASocket（如需跟踪 Socket 属性）
bind
sendto
WSASendTo
closesocket
```

每个出站数据报封装以下元数据：

```text
房间 ID / 会话 ID
发送玩家逻辑 IP
发送 Socket 的逻辑源端口
目标逻辑 IP
目标端口
广播或单播标记
UDP 载荷长度
原始 UDP 载荷
序列号/时间戳（传输层诊断使用，不能改变 UDP 语义）
```

搜索目标 `255.255.255.255:5739` 或房间 `.255:5739` 应转换为房间 fan-out，但不能发回发送者，除非实测 WE8 依赖本机回环副本。

### 11.4 入站 Hook 契约

无 TAP 时，普通 Winsock 无法让一个来自代理的本地数据报自然显示为 `10.222.x.x` 对端。推荐在 Hook 中直接向 WE8 合成接收结果：

```text
recvfrom / WSARecvFrom 返回：
  payload = 对端原始 WE8 UDP 载荷
  source sockaddr = 对端逻辑 IP + 对端原始逻辑端口
```

必须维护：

```text
(本地逻辑 IP, 本地逻辑端口, Socket 句柄)
    <->
(远端逻辑 IP, 远端逻辑端口, 房间成员)
```

不能把所有入站包都投给同一个 `5739` Socket。搜索客机随机端口、加入随机端口和主机固定端口必须正确分流。

### 11.5 接收就绪语义

这是无 TAP 方案最容易遗漏的部分。

如果 WE8 使用阻塞 `recvfrom`，Hook 可以等待本地代理队列；但如果 WE8 使用以下机制等待 Socket 可读：

```text
select
WSAEventSelect
WSAAsyncSelect
WSAWaitForMultipleEvents
重叠 I/O + 完成例程/事件
```

仅 Hook `recvfrom` 还不够，因为游戏可能永远不会被通知“有包可读”。开发前应增加 Winsock 调用追踪，确认 WE8 实际使用哪种等待机制，然后一并虚拟化对应 API。

### 11.6 广播转发规则

成功样本定义了最小广播行为：

```text
来源：客机逻辑IP:随机端口
目标：房间广播IP:5739
动作：发送给同房间其他在线节点
对端交付：保持来源逻辑IP和随机端口，目标交给本地 5739 Socket
```

主机回复规则：

```text
来源：主机逻辑IP:5739
目标：客机逻辑IP:搜索随机端口
动作：只投递给该客机和该逻辑 Socket
```

加入和比赛规则：

```text
按目标逻辑 IP 单播
保留双方逻辑端口
不解析、不合并、不拆分 WE8 UDP 数据报
```

### 11.7 传输层要求

用户态传输可选择自建 UDP、QUIC、WebRTC DataChannel 或其他成熟库，但必须满足：

- 房间隔离和鉴权。
- 中继兜底，不能只依赖 P2P 打洞。
- UDP 数据报边界不丢失。
- 延迟优先，不应使用会产生严重队头阻塞的单一可靠字节流承载全部比赛数据。
- 支持广播 fan-out 与逻辑单播。
- 支持玩家上下线和端点重绑定。
- 有包级日志，可关联发送节点、目标节点、逻辑五元组和传输路径。
- 对大于常见 MTU 的载荷有明确策略，但不要悄悄截断。
- 加密和防重放不能改变 WE8 可见的载荷。

### 11.8 无 TAP 方案不能再依赖的系统能力

移除 TAP 后将失去：

- Windows 自动 ARP。
- 系统 `10.222.x.0/24` 路由。
- 内核自动按 IP/端口分流。
- n2n 的二层广播复制。
- 普通 `ping 10.222.x.x` 诊断能力。

这些能力需要由逻辑地址表、Hook Socket 表、房间代理和平台内诊断取代。不能因为游戏界面仍显示 IP，就假设 Windows 系统真的拥有该 IP。

### 11.9 无 TAP 版本的分阶段开发路线

#### P0：调用观测

- 在不改变行为的情况下记录 WE8 的 Winsock 调用。
- 确认创建、绑定、搜索发送、等待、接收、加入和关闭 Socket 的准确 API 顺序。
- 确认同步、异步、重叠 I/O 使用方式。

#### P1：同机回环原型

- 两个测试进程或两台同局域网电脑通过用户态代理转发。
- 实现广播 fan-out 和单播映射。
- 验证客机能显示主机。

#### P2：完整加入与比赛

- 覆盖新的随机加入端口。
- 持续转发所有后续 UDP 数据报。
- 完成至少 10 分钟比赛，无断线、无明显卡顿。

#### P3：互联网中继

- 先保证所有玩家能通过中心 UDP 中继联机。
- 再增加 P2P 打洞作为延迟优化。
- P2P 失败必须自动回落中继，不能让游戏会话失败。

#### P4：兼容性

- Windows 10/11、多网卡、不同路由器和运营商。
- 防火墙开启状态。
- 不安装 TAP、不要求管理员权限。
- 与直播、语音、浏览器和其他 VPN 共存。

### 11.10 无 TAP 版本验收条件

必须同时通过：

1. 客机广播搜索能看到主机。
2. 双方互换主客机后仍能搜索。
3. 搜索列表连接成功。
4. 输入逻辑 IP 直连成功，或者产品明确取消该入口并提供等价平台连接。
5. 持续双向比赛至少 10 分钟。
6. Windows 防火墙开启时正常。
7. 两端存在多个物理/虚拟网卡时正常。
8. P2P 失败时中继仍能完成比赛。
9. Hook/代理崩溃不会遗留系统路由、驱动或防火墙污染。
10. 抓包或代理日志能还原每个逻辑 UDP 数据报的发送和交付路径。

## 12. 当前实现的维护约束

后续修改网络代码时必须保持：

1. 平台分配的同房间虚拟 IP 唯一。
2. n2n 外层绑定正常物理出口，不绑定 TAP。
3. WE8 内层 UDP 绑定 TAP，不影响其他应用流量。
4. 搜索广播目标使用当前房间定向广播地址。
5. 主机 `5739` 和客机随机端口双向可达。
6. 防火墙规则覆盖 Public、随机 UDP 端口和 ICMP 诊断。
7. Windows 7/10/11 防火墙配置不依赖 PowerShell COM。
8. TAP 通过 GUID 识别，不依赖中文/英文显示名称。
9. 路由只覆盖房间网段，不增加 TAP 默认路由。
10. Hook 必须在 WE8 恢复运行前确认初始化成功。

任何修改若破坏以上一项，都可能重新出现已经解决过的单向搜索、防火墙开启失败、绿色版重复创建 TAP 或多网卡绑定错误。

## 14. 最终结论

当前 TAP+n2n 方案的正确工作模型是：

```text
API 分配唯一 10.222 房间 IP
  -> edge 打开指定 TAP 并建立 n2n 房间二层网络
  -> 路由把房间网段指向 TAP
  -> 防火墙允许房间 UDP/ICMP 与 edge/WE8
  -> Hook 把 WE8 UDP Socket 绑定 TAP
  -> Hook 把全局搜索广播改为房间定向广播
  -> 客机随机端口广播到主机 5739
  -> 主机 5739 单播回复客机原随机端口
  -> 新随机端口继续完成加入和比赛
```

未来无虚拟网卡方案可以复用同一协议事实，但需要把 TAP/n2n 当前自动提供的 Socket 分流、来源地址、广播复制和接收就绪语义全部搬到 Hook 与用户态代理中。只做搜索广播转发不足以联机；完整方案必须同时虚拟化发送、接收、等待通知和逻辑地址映射。
